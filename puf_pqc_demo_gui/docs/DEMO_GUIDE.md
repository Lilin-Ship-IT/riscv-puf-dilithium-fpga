# 演示指南（DEMO_GUIDE）——10 分钟汇报脚本

本指南按新五页 GUI 编排，默认用**本机仿真**完成现场演示；最后附真板版开场与状态说明。台词可直接使用，链接图片均由真实 Windows 桌面渲染。

## 开场前检查

1. 在 `D:\FPGA\puf_pqc_demo_gui` 启动 `python main.py`。
2. 确认左侧有五页：演示首页、1 连接设备、2 固件与密钥、3 签名与验证、4 结果与日志。
3. 默认选择“本机仿真”，保持内置固件、DEV0 和默认 CHAL。
4. 若演示真板，先按 [BOARD_OPERATION_GUIDE.md](BOARD_OPERATION_GUIDE.md) 完成 openocd + gdb，确认 COM3 未被占用，并保持 SEED。
5. 主动说明种子来源，不把行为模型或 SEED 直注说成物理 PUF。

## 开场白（约 30 秒）

**本机仿真版：**

> “这是一套 PUF × Dilithium 可信启动演示上位机。它把 2KB 固件度量、256 bit 密钥种子、Dilithium2 密钥生成、签名和验签串成一条可观察的链路。今天现场用本机仿真，其中 PUF 是 SHAKE-256 行为模型，不是物理 PUF；协议、结果格式和既有硬件验证向量保持一致。”

**真板版：**

> “这次链路运行在真实开发板上，真板串口脚本已经实测 PASS。需要明确的是，当前板上还没有接物理 PUF，所以密钥种子采用 SEED 直注；本次验证的是 FPGA 设计、固件、Dilithium 签名链路和 PC 协议，而不是物理 PUF 的挑战—响应特性。”

## 第一幕：正常全链路（约 3 分钟）

**操作**：在“演示首页”点击 **“▶ 一键开始演示”**。默认本机仿真未连接时会自动连接。

**预期画面**：顶部出现“忙碌 · 一键演示全流程”和进度条（[06_demo_running.png](screenshots/06_demo_running.png)）；完成后自动进入“4 结果与日志”，绿色 **0 = PASS**（[05_results_logs.png](screenshots/05_results_logs.png)）。

**台词与翻页**：

1. “软件先上传 2KB 固件并计算 SHA3-256，摘要把后续签名绑定到这份固件。”
2. 进入 **“2 固件与密钥”**：“当前默认 CHAL 在行为模型中产生 256 bit R，再作为 Dilithium2 密钥种子；如果选 SEED，则是直接注入种子，二者必须明确区分。”（[03_firmware_keys.png](screenshots/03_firmware_keys.png)）
3. “密钥生成后，软件自动读取 1312B 公钥和 2528B 私钥。”
4. 进入 **“3 签名与验证”**：“私钥对固件摘要签名，得到 2424B 线上格式签名；再用公钥验签，绿色 0 = PASS，链路闭环。”（[04_sign_verify_pass.png](screenshots/04_sign_verify_pass.png)）
5. 回到 **“4 结果与日志”**：“这里能复制或导出三项结果，通信日志保留每一步命令和响应，方便复核。”

**加分句**：

> “默认 DEV0、默认挑战和内置固件下，摘要、行为模型 R、PUBK/PRIV 等与既有验证向量逐字节对拍；这不是把某次屏幕结果硬编码成演示结论。”

## 第二幕：篡改固件 → FAIL（约 2 分钟）

**操作**：进入“3 签名与验证”，点击 **“篡改固件 1 字节，再签名并验证”**。

**预期画面**：红色 **1 = FAIL**（[08_tamper_fw_fail.png](screenshots/08_tamper_fw_fail.png)）。

**台词**：

> “现在只改固件第 0 个字节。SHA3 的雪崩效应使摘要完全改变；对篡改摘要签名本身可以完成，但软件随后恢复原固件摘要，再验这份新签名，消息与签名不匹配，所以必须 FAIL。这展示的是固件完整性保护，而不是‘篡改后还能通过’。”

## 第三幕：篡改签名 → FAIL（约 1.5 分钟）

**操作**：先重新完成一次正常 SIGN，使当前签名和摘要处于一致上下文，再点击 **“篡改签名 1 字节，再验签”**。

**预期画面**：红色 **1 = FAIL**（[07_tamper_sig_fail.png](screenshots/07_tamper_sig_fail.png)）。

**台词**：

> “这次固件不动，只把签名第 50 字节翻转。验签执行的是真实 Dilithium 校验，不是比较字符串；签名内容被破坏后，红色 FAIL。”

## 第四幕：DEV0 → DEV1（约 2 分钟，本机仿真专属）

**操作**：确认使用本机仿真和 CHAL，进入“2 固件与密钥”，将“芯片”改为 **DEV1 (5a×32)**，再点击 **“生成密钥并读取 PUBK / PRIV”**。

**预期画面**：同一挑战下，R 前缀由 `7a472b83…` 变为 `1cc50e31…`，PUBK 前缀由 `ba5fa313…` 变为 `2fed1907…`（[09_dev1_keypair.png](screenshots/09_dev1_keypair.png)）。

**台词**：

> “行为模型用不同 DEVICE_CONST 模拟不同设备，所以同一挑战会产生不同响应和密钥对。这用来解释 PUF 唯一性在系统中的数据流意义，但它是模型假设，不是两颗物理 PUF 的实测证据。RTL 当前固定 DEV0，真板 SEED 演示也不做这个环节。”

## 真板状态补充（约 1 分钟，可选）

**操作**：展示“1 连接设备”的真实开发板设置（[10_serial_mode.png](screenshots/10_serial_mode.png)），不要在同一串口上同时启动 GUI 和命令行脚本。

**台词**：

> “真实开发板已经跑通 FW、SEED keygen、读取密钥、SIGN、VER 和篡改拒绝，`board_demo_run.py` 真板 PASS。FPGA 设计已成功做 FLASH 持久化，上电后设计仍在；但处理器固件目前每次上电仍需 openocd + gdb 下载并 resume。后续接入物理 PUF 并确认链路后，再把密钥方式从 SEED 改为 CHAL。”

## 结尾 30 秒总结

> “这套平台展示三点：第一，固件摘要与 Dilithium 签名绑定，固件或签名改一个字节都会被拒绝；第二，五页 GUI 把连接、密钥、签名、结果和日志完整串起来，同一协议可切换本机、RTL 和真实开发板；第三，验证边界说清楚——本机和 RTL 的 PUF 是行为模型，当前真板用 SEED 直注，真板链路已 PASS，但不冒称物理 PUF 已验证。”

## Q&A 预案

**Q：现在用的是真 PUF 吗？**  
不是。本机仿真和 RTL 仿真使用 `R = SHAKE-256(C ‖ DEVICE_CONST)` 行为模型；当前真实开发板未接物理 PUF，使用 SEED 直注。只有后续接入物理 PUF 并实际验证 CHAL 链路后，才能声明物理 PUF 结果。

**Q：真实串口是否已经在真板验证？**  
是。`board_demo_run.py` 使用 COM3 完成全链路，正常验签 `OK`，篡改签名后 `FAIL`。但这不改变“当前无物理 PUF”的边界。

**Q：FLASH 已持久化，为什么每次上电还要下载固件？**  
FLASH 中持久化的是 FPGA 设计；`test_board_uart0.elf` 处理器固件目前没有上电自动运行流程。每次上电仍需 openocd + gdb `load`、设置入口并 `monitor resume`。

**Q：为什么当前真板默认 SEED，而不是 CHAL？**  
CHAL 需要物理 PUF 挑战—响应链路，当前板上尚未接入。SEED 让其余固件度量、密钥生成、签名和串口协议可以先独立验收，同时不伪造 PUF 结论。

**Q：DEV0/DEV1 是否证明物理不可克隆性？**  
不证明。它们只是本机行为模型的两个设备常数，用于演示“设备差异 → 响应差异 → 密钥差异”的数据流。物理不可克隆性必须由真实 PUF 器件和实验数据验证。

**Q：0 = PASS / 1 = FAIL 是否写反？**  
没有。界面沿用当前固件与硬件核的结果语义：0 表示接受，1 表示拒绝；绿色 PASS 和红色 FAIL 已明确标出。

**Q：私钥为什么直接显示和导出？**  
这是演示验收要求，用于核对 2528B PRIV 和协议格式，不是产品级密钥管理。真实产品应限制私钥出域，并设计清零和访问控制。

**Q：RTL 一键演示为什么很久？**  
RTL 模式逐拍运行 E203 和 Dilithium 核，大帧还要逐位注入 UART，完整流程约 45～60 分钟。现场快速演示用本机仿真，RTL 用于验证而非追求演示速度。

**Q：真板连不上先查什么？**  
先查本次上电后是否完成 gdb 下载和 `monitor resume`，再查 COM3 是否被占用、115200 8N1 是否正确、openocd/JTAG 是否正常。完整决策顺序见 [BOARD_OPERATION_GUIDE.md](BOARD_OPERATION_GUIDE.md)。
